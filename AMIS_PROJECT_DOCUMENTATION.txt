  1. SYSTEM OVERVIEW
================================================================================

AMIS (Asset Management Information System) is a web-based government portal
built for the Department of Information and Communications Technology (DICT).
It manages property and stock assets — tracking issuance, transfers, returns,
disposals, maintenance, inventory counts, and reports.

The system is a pure front-end application (HTML + CSS + Vanilla JS).
No build tools, no frameworks, no npm. Everything runs directly in the browser.
A real back-end API is expected to replace the mock/stub functions in the future.

Key characteristics:
  - No page reloads between sub-views (single-page shell per section)
  - URL query parameters drive which sub-view is active (?op=KEY, ?view=KEY)
  - Session is stored in sessionStorage (not localStorage)
  - All shared UI (sidebar, header, loader, toasts, modals) is injected by
    layout.js — page scripts never touch the sidebar or header directly

  3. CORE ARCHITECTURE
================================================================================

  Every page (except login) follows this exact pattern:

  HTML HEAD:
    <script>
      window.AMIS_PAGE = { id: 'page-id', title: 'Page Title' };
    </script>
    <script src="../../common/common.js"></script>
    <script src="../../common/layout.js"></script>

  HTML BODY:
    <div id="layout-root"></div>      ← layout.js injects sidebar + header here
    <div id="page-body">              ← layout.js MOVES this into .page-content
      ... page content ...
    </div>
    <script src="page.js"></script>   ← page script runs AFTER layout is ready

  Page scripts listen for the custom event before touching the DOM:
    document.addEventListener('amis:layout-ready', () => { ... });

  The 'amis:layout-ready' event is dispatched by layout.js after it finishes
  injecting the sidebar, header, and moving #page-body into place.

  ── 3a. common.css ────────────────────────────────────────────────────────────

  Loaded on every page. Defines:
    - CSS custom properties (--primary, --accent, --border, --shadow-*, etc.)
    - DICT brand colors: --primary (#0A3D7C), --primary-dark (#062B5B)
    - Philippine flag colors: --ph-blue, --ph-red, --ph-yellow
    - Base reset (box-sizing, margin, padding)
    - Typography: Inter (body), Barlow (headings, buttons)
    - Utility classes: .hidden, .flex, .gap-*, .text-center, etc.
    - Toast notification styles (#toast-container, .toast, .toast.success, etc.)
    - Page loader styles (#page-loader, .loader-spinner)
    - Modal overlay styles (.modal-overlay, .modal, .modal-close)
    - Global scrollbar styles

  ── 3b. common.js ─────────────────────────────────────────────────────────────

  Loaded on every page. Exposes four global objects:

  Toast
    .show(message, type, duration)
    Types: 'success' | 'error' | 'warning' | 'info'
    Duration defaults to 3500ms.
    Auto-creates #toast-container if not present.

  Loader
    .show(text)   ← shows fullscreen dark overlay with spinner
    .hide()       ← fades out and removes the loader

  Auth
    .setSession(userData)   ← saves user object to sessionStorage
    .getSession()           ← returns parsed user object or null
    .clearSession()         ← removes session
    .isLoggedIn()           ← returns boolean
    .requireAuth(redirect)  ← redirects to login if not logged in
    .requireGuest(redirect) ← redirects to dashboard if already logged in
    Session key: 'amis_session'

  Modal
    .open(id)                    ← adds .open class to overlay element
    .close(id)                   ← removes .open class
    .closeOnOverlayClick(id)     ← wires click-outside-to-close behavior

  Form
    .validate(fields)            ← validates array of {el, rules} objects
    .setFieldError(el, message)  ← shows/clears inline field error
    .clearErrors(form)           ← removes all validation states from a form
    Rules supported: 'required', 'email', 'minLength:N'

  ── 3c. layout.css ────────────────────────────────────────────────────────────

  Loaded on every page except login. Defines:
    - .app-shell (flex container for sidebar + main-wrapper)
    - .sidebar (fixed left nav, 256px expanded / 68px collapsed)
    - .sidebar.collapsed — collapses sidebar, hides labels
    - .main-wrapper (right side, holds header + page-content)
    - .top-header (70px fixed top bar with breadcrumb + user dropdown)
    - .page-content (scrollable main area, 24px/28px padding)
    - .user-dropdown (absolute dropdown from header avatar)
    - .sidebar-overlay (mobile backdrop)
    - Submenu styles: .nav-item--has-children, .nav-sub-list, .nav-sub-link
    - Nav tooltip: #nav-float-tip (shown when sidebar is collapsed)
    - .dash-page-header, .dash-page-title, .dash-page-sub (page top area)
    - Responsive breakpoints: 1024px (collapse sidebar), 720px (hide labels)

  ── 3d. layout.js ─────────────────────────────────────────────────────────────

  Loaded on every page except login. Responsibilities:
    1. Builds the full sidebar HTML from NAV_ITEMS and OP_ITEMS / VIEWS_ITEMS
    2. Injects it into <div id="layout-root">
    3. Moves <div id="page-body"> into .page-content (no innerHTML cloning)
    4. Reads window.AMIS_PAGE.id to set the active nav item
    5. Reads ?op= or ?view= URL params to set active sub-nav item
    6. Handles sidebar collapse (persisted in localStorage: 'amis_sidebar_collapsed')
    7. Handles Operation Module submenu toggle (#nav-op-toggle)
    8. Handles Views submenu toggle (#nav-views-toggle)
    9. Handles mobile overlay (#mobile-menu-btn, .sidebar-overlay)
    10. Handles user dropdown (#user-dropdown-btn, .user-dropdown)
    11. Populates user info (name, role, avatar initials) from Auth.getSession()
    12. Handles sign out (#signout-btn)
    13. Dispatches 'amis:layout-ready' custom event when done

  NAV_ITEMS order in sidebar:
    Dashboard → System → User Management → Files Data →
    Operation Module (expandable) → Sticker Tag → Views (expandable) → About

  4. AUTHENTICATION & SESSION
================================================================================

  - Session is stored in sessionStorage under key 'amis_session'
  - Session object shape:
      {
        id:      'usr_<timestamp>',
        name:    'Full Name',
        email:   'user@dict.gov.ph',
        role:    'Administrator' | 'Staff',
        loginAt: '<ISO timestamp>'
      }
  - Login page calls Auth.requireGuest() — redirects away if already logged in
  - All other pages call Auth.requireAuth() — redirects to login if not logged in
  - Sign out clears session, shows loader, then redirects to login after 900ms

  6. CHANGED: OPERATION MODULE – SUB-VIEW ARCHITECTURE (OPTION C)
================================================================================

  BEFORE (original):
  ─────────────────
  operation-module/
  ├── operation-module.html
  ├── operation-module.css
  └── operation-module.js     ← contained ALL 20 sub-view definitions inline
                                 (labels, groups, column arrays) in one large

  The original operation-module.js had a single loadOp(key) function that
  read from that internal OPS object, built the table header, and rendered
  an empty table. All 20 sub-views shared the exact same rendering logic
  with no way to add view-specific behavior (filters, API calls, etc.)
  without bloating the single file further.

  AFTER (current):
  ────────────────
  operation-module/
  ├── operation-module.html   ← updated: loads all ops/*.js before router
  ├── operation-module.css    ← unchanged
  ├── operation-module.js     ← now a THIN ROUTER only (no sub-view data)
  └── ops/                    ← NEW folder, one file per sub-view
      ├── goods-receive.js
      ├── tagging.js
      ├── property-information.js
      ├── property-issuance.js
      ├── stock-issuance.js
      ├── property-request.js
      ├── stock-request.js
      ├── property-transfer.js
      ├── property-return.js
      ├── property-return-request.js
      ├── stock-return.js
      ├── property-maintenance-request.js
      ├── property-maintenance.js
      ├── property-verification.js
      ├── property-gate-pass-request.js
      ├── inventory-count.js
      ├── personal-property-gate-pass-request.js
      ├── property-disposal.js
      ├── property-disposal-request.js
      └── stock-disposal.js

  HOW IT WORKS:
  ─────────────
  Each file in ops/ registers itself on window.OP_VIEWS:

    window.OP_VIEWS = window.OP_VIEWS || {};
    window.OP_VIEWS['goods-receive'] = {
      label:    'Goods Receive',
      group:    'Receiving & Tagging',
      columns:  ['GRR No.', 'Date Received', ...],
      onLoad:   function(container) { /* view-specific logic */ },
      onUnload: function()           { /* cleanup */ },
    };

  operation-module.js (the router) does:
    1. Reads ?op=KEY from the URL
    2. Looks up window.OP_VIEWS[key]
    3. Calls onUnload() on the previously active view (if any)
    4. Updates the page title, breadcrumb, document.title
    5. Hides the landing grid, shows the content card
    6. Builds the <thead> from op.columns
    7. Resets <tbody> to "No records found"
    8. Shows toolbar, table wrap, footer, export/add buttons
    9. Calls onLoad(container) on the new view
    10. Exposes window.OP_LOAD(key) globally for programmatic switching

  SCRIPT LOADING ORDER in operation-module.html:
    All ops/*.js files MUST be loaded before operation-module.js
    so that window.OP_VIEWS is populated before the router runs.

    <script src="ops/goods-receive.js"></script>
    <script src="ops/tagging.js"></script>
    ... (all 20 ops files) ...
    <script src="operation-module.js"></script>   ← LAST

  WHY THIS APPROACH:
    - Each sub-view's unique logic (filters, date pickers, API calls,
      custom form fields, etc.) lives in its own isolated file
    - The router (operation-module.js) stays small and never needs editing
      when adding or modifying a sub-view
    - onUnload() allows proper cleanup (removing event listeners, clearing
      timers) before switching to another sub-view
    - URL routing (?op=KEY) continues to work exactly as before
    - window.OP_LOAD(key) allows the landing tiles to trigger a load
      programmatically if needed

  14. BACKEND / DATABASE – Supabase (2026-07 migration in progress)
================================================================================

  AMIS is being migrated from a fully static front-end to a real backend
  powered by Supabase (managed Postgres + auth + auto REST/JS API).
  The static pages will call Supabase directly from the browser using the
  anon public key; Row-Level Security (RLS) enforces authorization.

  Files added:
    db/01_schema.sql          Full Postgres schema (auth profiles, master
                              data, operational transactions, audit trail).
    db/02_rls.sql             Row-Level Security policies. Authenticated
                              users can read; Administrators can write.
    db/03_seed.sql            Optional seed data (regions, UoM, categories,
                              classifications, security questions).
    common/config.example.js  Template for Supabase credentials.
    common/config.js          Local copy with real URL + anon key
                              (GIT-IGNORED — never commit).
    common/supabase.js        Loads @supabase/supabase-js v2 and exposes
                              window.AMIS_DB + window.AMIS_READY promise.

  Setup checklist (once per environment):
    1. Create a free Supabase project at https://supabase.com.
       Choose the Southeast Asia (Singapore) region for lowest latency.
    2. Project Settings → API → copy Project URL and anon public key.
    3. Copy common/config.example.js → common/config.js and paste values.
    4. In Supabase → SQL Editor → New query:
         - paste db/01_schema.sql   → Run
         - paste db/02_rls.sql      → Run
         - paste db/03_seed.sql     → Run  (optional but recommended)
    5. Authentication → Providers → Email → enable "Confirm email" OFF for
       development, ON for production.
    6. Create the first Administrator:
         Authentication → Users → Add user → email + password.
         Then in SQL Editor:
           update public.profiles set role = 'Administrator'
           where email = 'you@dict.gov.ph';

  Migration phases:
    Phase 1 (done, commit 22e94b9 / a1f0937):

================================================================================
  15. USER ROLES & PERMISSIONS
================================================================================

  Roles (defined by user_role enum in db/01_schema.sql):
    Administrator   Full access. Can approve, invite users, edit master
                    data, modify any record. Only role that RLS allows to
                    write to reference/operational tables.
    Staff           Regular user. Can read all data, submit requests,
                    tag their own property issuances. Cannot approve.
    Viewer          Read-only. Cannot submit or edit anything.

  How to promote a user to Administrator:
    Supabase Dashboard → SQL Editor:
      update public.profiles set role='Administrator'
       where email='them@dict.gov.ph';

  How to invite a new user (admins only):
    Supabase Dashboard → Authentication → Users → Add user
      → Create new user → email + password → check "Auto Confirm User"
      → Create user.
    The public.handle_new_user() trigger auto-creates the
    matching public.profiles row with role='Staff'.
